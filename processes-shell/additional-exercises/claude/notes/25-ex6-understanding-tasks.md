## Concrete, hands-on things to run — each targeting one specific blind spot

**1. `-fsanitize=address` (AddressSanitizer, ASan).** This is the single highest-leverage tool for exactly your confusion, because it makes dangling-ness *empirically observable at runtime* instead of something you have to reason about statically. Compile any of your buggy exercises with `gcc -fsanitize=address -g -o prog prog.c` and run it — ASan poisons freed/out-of-scope memory and will print a detailed report (including a stack trace of *where the object was allocated* and *where it was freed/went out of scope*) the instant you touch it after death. Concept it directly targets: **making $L(a)$'s endpoint a real, instrumented event you can watch happen**, rather than an abstraction you compute by hand. Run your Exercise 1, 3, and 5 code through it — watch it catch each one, and read the "freed by thread T0 here" / "previously allocated by thread T0 here" trace it prints, since that trace is a literal printout of $\mathrm{owner}(t,a)$'s history.

**2. `readelf -S ./a.out` or `size -A ./a.out`.** Run this on a compiled binary containing both a string literal and a stack-local buffer. You'll see distinct sections: `.rodata` (string literals live here — read-only, hence the segfault-on-write from earlier), `.data`/`.bss` (globals/statics), and *no section at all* for stack or heap — because those don't exist in the binary image; they're runtime-only regions the OS sets up. Concept targeted: **static storage duration is literally baked into the compiled file**; automatic and allocated storage durations are not — they're events that happen only when the program runs. Seeing "`.rodata` exists as bytes on disk before the program even starts" versus "the stack frame doesn't exist until you call the function" makes the *kind*-of-lifetime distinction physically concrete.

**3. `printf("%p\n", ptr)` on every pointer in a small test program, then diff the ranges.** Print the address of a string literal, a stack-local variable, a `malloc`'d block, and a global — all in one run. On Linux you'll typically see them fall into wildly different numeric ranges (stack addresses near the top of the address space, heap addresses much lower, `.rodata`/`.data` addresses near the binary's load address). Concept targeted: **$\mathrm{addr}(a)$ is not just abstract notation — it's a literal number you can print, and which range it falls in tells you its storage duration**, empirically, no reasoning required.

**4. `cat /proc/<pid>/maps` while your program is paused (e.g., stopped in gdb, or with a `sleep()` inserted).** This dumps the kernel's actual VMA list — the real $\mathrm{addr}$ function for every region: stack, heap, each loaded library's `.text`/`.rodata`/`.data`, with permission bits (`r-x`, `rw-`, etc.) shown per region. Concept targeted: this is the OS-level grounding from a few turns ago made literal — you're looking at the actual data structure the kernel uses to decide "is this address currently valid, and with what permissions," which is the mechanism underneath every `Safe`/dangling judgment you've been computing by hand.

**5. `gdb` with `watch` on a specific address.** Set a breakpoint right after `first = tokens[0]`, note `first`'s value with `print first`, then `watch *(char*)0xADDRESS` and continue — watch what happens (or doesn't) as `realloc` runs. Then do the equivalent for Exercise 5: watch `joined`'s address, step through the `return`, and inspect what's now sitting at that same address once you're back in the caller (it'll usually still show `"ls "` or similar for a few instructions, then get clobbered by the next function call — reproducing the "looks fine, then randomly doesn't" symptom you now understand mechanically). Concept targeted: **watching the same address survive across an event (realloc) versus decay across an event (return)**, side by side, in real time.

**6. `objdump -d` on the compiled `classify_command`, specifically looking at what happens to the stack pointer around the `return`.** You'll see the compiler emit something like `add $0x110, %rsp` (deallocating the frame by moving the stack pointer) right before `ret`. Concept targeted: **frame death is one specific, visible machine instruction** — not a mysterious language-level event, a literal arithmetic operation on a register, which is the OS/hardware grounding for why "the bytes are often still there" (nothing zeroed them, the instruction just moved a pointer) and why the next function call is what actually clobbers them (its own prologue writes into that now-unprotected region).

**Do them in this order** — ASan first (it'll *tell you* where the bugs are without you needing to trust your own static analysis yet), then the `readelf`/`/proc/maps` pair (grounds *why* static vs. automatic differ at the OS level), then gdb/objdump (lets you watch the exact instructions responsible for each lifetime boundary firing). By the time you've done all five on your own Exercise 1, 3, and 5 code, the type-vs-storage-duration distinction won't be a concept you're holding onto by argument — you'll have watched it happen.
